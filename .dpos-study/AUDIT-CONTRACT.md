### K-1. Governance через `setBlsVerifier` получает право tombstone'ить любого валидатора и забирать весь его самостейк

`Код:` `config.rs:717-731` (сеттер верификатора без задержки и без проверок кроме ненулевого адреса), `config.rs:412-426` (сеттер `slash_fund_address`), `consensus.rs:1084-1163` (`slash_from_evidence`: личность и обе подписи проверяются исключительно ответами верификатора), `consensus.rs:974-990` (получатель конфискации — `slash_fund_address`), `consensus.rs:151-193` (PoP при регистрации тоже проверяется верификатором).

`Механизм:`
1. Governance вызывает `setSlashFundAddress(A)` и `setBlsVerifier(V)`, где `V` — контракт, который на `compressG2Unchecked` возвращает 96 байт, равные зарегистрированному ключу жертвы (`keccak(compressed)` → `bls_pubkey_owner`, `consensus.rs:1099-1102`), на `compressG1Unchecked` — байты подписей из blob, на `verify` — `true`.
2. Любой адрес вызывает `slashEquivocationNotarize(blob, pk, sig1, sig2)` с синтаксически корректным blob (`evidence.rs:185-193`) — никакой другой проверки нет.
3. `apply_equivocation_penalty` (`consensus.rs:1008-1041`): tombstone, JAIL, вывод из `active_validators`, невидимость с next_epoch, `seize_self_stake` → `try_transfer(A, самостейк + pending_undelegated)`.
4. Повторить для каждого валидатора. Дополнительно тот же `V` пропускает любой PoP → регистрация валидаторов с чужими/несуществующими ключами.

`Последствие:` два governance-вызова превращают permissionless-вход в кран, которым любой адрес конфискует самостейк всех валидаторов на адрес, выбранный governance, и выводит их из консенсуса навсегда (tombstone не снимается, `consensus.rs:1019-1022`; сброса нигде нет). Компрометация одного governance-ключа = потеря всех самостейков и полная смена комитета.

`Условия:` ключ governance (или его компрометация). Никакой задержки/таймлока на смену верификатора нет.

`Тег:` SERIOUS (класс «governance с избыточными правами»; по последствию — кража средств, но требует governance).

`Уверенность:` [KNOWN].

`Расхождение с CONTRACT-UNDERSTANDING:` §10 перечисляет `bls_verifier` как «gov, сразу», но не связывает это со слэшингом и фондом. Дополнение, не противоречие.

### K-2. Доказательство эквивокации не привязано ни к комитету, ни к эпохе, ни к развёртыванию — только к `chain_id`

`Код:` `consensus.rs:921-930` (namespace = `"FLUENT_DPOS_V1_" ‖ chain_id ‖ "_KIND"`), `consensus.rs:1099-1105` (личность только по ключу), `consensus.rs:1163` (`evidence.epoch` идёт только в событие), `consensus.rs:1115-1118` (`activation_epoch` читается, но с эпохой доказательства не сравнивается), `evidence.rs:286-296` (signer index читается и не используется).

`Механизм:` подпись валидатора под любыми двумя конфликтующими `Proposal` с одинаковыми `(epoch, view)` под этим namespace достаточна. Namespace содержит `chain_id`, но не genesis hash, не адрес контракта, не эпоху активации ключа. Сценарии:
- Сеть перезапущена с нуля с тем же `chain_id` (по проектной практике сети перезапускаются с блока 0), валидатор использует тот же BLS-ключ. На старой сети он честно голосовал за `(epoch=7, view=42, payload=X)`, на новой — за `(7, 42, payload=Y)`. Две честные подписи с разных сетей = валидное `ConflictingNotarize` на новой сети.
- Та же пара ключ+chain_id на devnet/testnet и в другой инсталляции.
- Подписи, сделанные до `activation_epoch` ключа (ключ уникален навсегда, `consensus.rs:237-248`, так что это только про сети-двойники).

Тест `tests.rs:6820-6861` закрепляет, что незафиксированная эпоха в доказательстве не блокирует слэш — то есть отсутствие привязки намеренно, но следствие для сетей-двойников нигде не рассмотрено.

`Последствие:` честный валидатор tombstone'ится и лишается самостейка чужим действием (любой адрес может отправить доказательство).

`Условия:` две сети с одинаковым `chain_id` и общим BLS-ключом валидатора, или любой источник двух подписей одного ключа под одним namespace. Проверка совпадения `chain_id` между релизами devnet/prod — вне этого дерева (ГИПОТЕЗА, что совпадение бывает).

`Тег:` SERIOUS при совпадении `chain_id`; MINOR, если `chain_id` уникален для каждого развёртывания и ключи не переиспользуются.

`Уверенность:` [KNOWN] по механизму; условие — ГИПОТЕЗА.

`Расхождение с CONTRACT-UNDERSTANDING:` §15.11 ставит вопрос, ответ: да, это дефект (см. часть V).

### K-3. Комитет можно опустить ниже 4 действием одного участника, после чего `commitEpochCommittee` ревертит и цепь останавливается

`Код:` `consensus.rs:718-720` (revert `CommitteeTooSmall` при `< MIN_COMMITTEE_LENGTH`), `staking.rs:917-928` (`disableValidator`: без проверки числа видимых), `staking.rs:1295-1300` (полный выход владельца → `deactivate_validator_at`, без проверки), `consensus.rs:1023-1028` (слэш → невидимость, без проверки), `staking.rs:334-347` (единственное место, где такая проверка есть — `apply_production_exclusion`). Узел: `~/Work/fluentbase/crates/node/src/evm.rs:995-1023` — неуспех `commitEpochCommittee` = `BlockExecutionError`, `evm.rs:925-948` — драйвер коммитит каждый блок, пока `next ≤ current+2`.

`Механизм:` видимых валидаторов на эпоху отбора ровно 4 (cap обрезает только сверху, снизу ничего не добавляет). Владелец одного делает `undelegate` всего самостейка (у него нет чужих делегаций) → `deactivate_validator_at(current)` → невидим с `current+1`. При следующем блоке узел коммитит `target = current+3`, отбор из `current+1` даёт 3 → revert → `BlockExecutionError` на каждом узле. Транзакцией это уже не починить: коммит — pre-execution системный вызов, он ревертит до выполнения любой транзакции (что и написано в `consts.rs:412-415`, и это подтверждено кодом узла).

То же — `disableValidator` от governance (даже одиночный, при 4 видимых), слэш по доказательству от любого адреса при 4 видимых.

`Последствие:` остановка цепи без пути восстановления через транзакции; требуется перезапуск с правкой генезиса.

`Условия:` число видимых валидаторов на эпохе отбора равно 4 (или в общем случае ≤ 4 + число одновременно выходящих). У малой сети/devnet это штатное состояние. Атакующему нужен один валидатор из четырёх (или ключ governance, или два конфликтующих голоса одного из четырёх).

`Тег:` BLOCKER по шкале («системный вызов узла может быть приведён в состояние, где он ревертит и цепь встаёт; действием одного участника»); условие — малый комитет. Проектное решение «принимаем BFT-границу» это покрывает лишь для случая слэша; для добровольного выхода и `disableValidator` защиты нет вообще, хотя для исключений по liveness она есть (`staking.rs:344`).

`Уверенность:` [KNOWN].

`Расхождение с CONTRACT-UNDERSTANDING:` §6.2 упоминает только «недобор после фильтра ключей»; пути через выход/disable/слэш не названы.

### K-4. После полного выхода владелец может вернуться с самостейком ниже `minValidatorStakeAmount` и быть активирован

`Код:` `staking.rs:891-893` (активация проверяет только `!= 0`), `staking.rs:1081-1119` (`delegate_to` не различает владельца; порог — `min_staking_amount`), `staking.rs:1228-1230` (`owner_self_stake` считается по `delegator == owner`), комментарий `staking.rs:884-890`: «self-stake here is either zero or at least the threshold that governed it when it was posted».

`Механизм:` владелец с самостейком S ≥ min_validator: `undelegate(S)` (нет чужих делегаций) → PENDING, очередь `(0, next)`. Затем `delegate(validator, min_staking_amount)` от того же адреса — принимается (`amount ≥ min_staking_amount`, валидатор существует, не tombstoned). `delegated_amount_at(owner, next_epoch)` = min_staking_amount ≠ 0 → `activateValidator` проходит. При `min_staking_amount = 1 BLEND`, `min_validator_stake = 100 BLEND` валидатор ACTIVE с 1 BLEND самостейка.

`Последствие:` требование минимального самостейка обходится; комментарий над проверкой утверждает обратное (расхождение комментарий/код — само по себе находка).

`Условия:` владелец валидатора + governance-активация (governance видит статус PENDING, но не самостейк).

`Тег:` MODERATE.

`Уверенность:` [KNOWN].

### K-7. История видимости глубиной 3 + отстающий коммит = ложный «невидим» и потенциальный `CommitteeTooSmall`

`Код:` `staking.rs:260-283` (эпохи ниже `prev2_from` → `false`), `staking.rs:217-258` (один переход на эпоху), `consensus.rs:706-717` (target может быть ≤ current, sel = target−2 ≥ current−2).

`Механизм:` при `target == current` (коммит отстал на 2) sel = current−2. Валидатор с переходами в эпохах current−1, current, current+1 (например, исключён → освобождён → отключён governance) имеет `prev2_from = current−1`, и sel < prev2_from → `false`, хотя в current−2 он был видим. Если таких несколько — комитет < 4 → revert.

`Условия:` отставание коммита на 2 эпохи. По коду узла (`evm.rs:925-948`) драйвер коммитит каждый блок, значит отставание возникает только после остановки и перезапуска с догоняющим коммитом — то есть ровно тогда, когда цепь и так восстанавливают.

`Тег:` MINOR (по последствию MODERATE, но условие требует уже произошедшего сбоя).

`Уверенность:` [KNOWN] по коду контракта; [LIKELY] по невозможности отставания в норме (не проверено, что драйвер запускается и на догоняющем пути с тем же `current_epoch`).

## Часть B — упрощения, включая архитектурные

### B-0. Три места наибольшей сложности относительно того, что они делают

1. **Отбор комитета «на эпоху в прошлом»**: roster (`staking.rs:175-215`), трёхуровневая история видимости (`storage.rs:139-154`, `staking.rs:217-283`), чекпоинты cap (`config.rs:263-302`), снапшоты стейка по эпохам с бинарным поиском (`staking.rs:484-595`), фильтр ключей по `activation_epoch` (`consensus.rs:538-552`) — пять независимых «эпохо-адресованных» механизмов существуют только ради одного свойства: `commitEpochCommittee` может быть вызван в любой момент и должен воспроизвести состояние эпохи `target−2`. Узел (`evm.rs:925-948`) вызывает его каждый блок и никогда не отстаёт; свойство нужно только на бумаге.
2. **Начисление и оплата стипендии**: `assign_epoch_shares` → `assigned_at_close_p1` (+1-кодирование) → self-call с лимитом топлива → `settle_up_to` с курсором и `MAX_SETTLE_CATCHUP` → `pay_epoch` с тремя исходами (revert/skip/pay) → claim-гейт по курсору (`staking.rs:1936-2173`, `liveness.rs:491-503`, `storage.rs:298-315`). Всё это — чтобы контракт сам тянул токены из чужого кошелька по `transferFrom` при закрытии эпохи и переживал отказ.
3. **Два маршрута слэшинга с разными понятиями личности** плюс собственный парсер wire-формата commonware в контракте (`consensus.rs:801-822` vs `973-1060`, `evidence.rs` целиком, 744 строки). Узел уже проверяет то же доказательство до голосования (`application.rs:709`).

### B-1. Коммит никогда не ревертит: при недоборе переиспользуется предыдущая запись

`Что сейчас:` `consensus.rs:718-720` — revert `CommitteeTooSmall`; узел превращает его в остановку цепи (`evm.rs:1013-1023`).

`Чем плохо:` K-3 (BLOCKER-класс от одного участника), K-7, K-16; единственная проверка-предохранитель есть только у liveness-исключений (`staking.rs:344`), у трёх других путей — нет, и любая новая причина невидимости снова откроет дыру.

`Как иначе:` в `commit_epoch_committee` при `members.len() < MIN_COMMITTEE_LENGTH` — не revert, а `record = committee_at(target−1).0`, `length = прежняя`, веса переписываются из прежнего кольца (или помечаются недоступными), `dkg_qual[target] = false`, событие `CommitteeCarriedOver(target, eligible_count)`. Для `target == 0` без 4 членов — единственный оставшийся revert (генезис, чинится правкой генезиса). Все проверки «не опускай ниже 4» в `disableValidator`/`undelegate`/слэше становятся ненужными; `apply_production_exclusion` можно оставить как есть.

`Что ломает:` ABI — нет (новое событие). Хранилище — нет. Узел: должен понимать, что комитет эпохи может совпасть с предыдущим при `dkg_qual = false` — он уже так работает для неизменившегося состава. Tombstoned член в переиспользованном комитете — узел его маскирует (по памяти проекта, tombstone severance в узле есть; здесь не перепроверено — [LIKELY]).

`Что это закрывает:` K-3 целиком, K-7, K-16 (частично: генезис остаётся).

### B-2. Отбор по текущему состоянию в момент коммита; удалить roster, историю видимости, чекпоинты cap и `getValidatorsWithKeysAt`

`Что сейчас:` см. B-0 п.1. Плюс `WARMUP_DELAY = 2` и `MAX_COMMITTEE_LOOKAHEAD_EPOCHS = 2` — два независимых числа, которые «случайно совпадают» (`consts.rs:436-437`).

`Чем плохо:` K-6 (cap до активации), K-7 (глубина истории), K-30 (roster растёт вечно, два обхода на коммит и по одному на каждый stamp), K-17 (два разных «отбора на эпоху»), расхождение live-view и коммита (`staking.rs:410-429` vs `385-392`). Инвариант «эпоха заморожена» держится на согласованности пяти механизмов и трёх задержек (+1 видимость, +2 делегация, −2 отбор).

`Как иначе:` коммит для `target = current + 2` читает **текущее** состояние: `active_validators` (статус ACTIVE и не под исключением — один бит `excluded_until` в `ProductionValidatorStorage`, уже есть `readmit_at_epoch`), стейк — `validator_total_at(current)` (снапшоты по эпохам остаются, они нужны наградам), cap — скаляр. Записанный комитет и кольцо весов — единственная «заморозка». Убираются: `selection_roster`, `selection_membership`, `set_selection_visible`, `selection_visible_at`, `selection_candidates_at`, `count_selection_visible_at`, `cap_checkpoints`, `active_validators_length_at`, `getActiveValidatorsLengthAt`, `getValidatorsWithKeysAt`, `committeeSelectionEpoch`, `selected_validators_at`/`selected_addresses_at`; `apply_production_exclusion` сводится к записи `readmit_at_epoch` и проверке `active.len() − excluded > cap`. Условие корректности: коммит вызывается ровно один раз на эпоху, что узел и делает (`evm.rs:925-948`); при отставании — B-1.

`Что ломает:` ABI — удаляются 3 селектора view без потребителя в узле (`getActiveValidatorsLengthAt`, `getValidatorsWithKeysAt`, `committeeSelectionEpoch`; grep по узлу: ни один не читается). Хранилище — удаляются два поля `StakingStorage` и одно `ChainConfigStorage` (контракт не задеплоен). Узел — правка не нужна.

`Что это закрывает:` K-6, K-7, K-17, K-30; упрощает K-3 (вместе с B-1).

### B-3. Стипендия из баланса контракта, без self-call и без курсора оплаты

`Что сейчас:` `pay_epoch`/`settle_up_to`/`settle_stipend_leg`/`assigned_at_close_p1`/`last_rewarded_epoch_p1` (`staking.rs:2073-2173`, `liveness.rs:491-503`, `storage.rs:298-315`, `consts.rs:447-491`); claim-гейт по курсору в трёх местах (`staking.rs:1357-1360`, `1484`, `1659-1664`).

`Чем плохо:` K-15 (мёртвый системный селектор с ловушкой), K-26 (глобальная заморозка наград при отставании курсора), гипотеза о семантике вложенного фрейма (T-5: тесты эмулируют фрейм клоном с общим хранилищем), самый дорогой и самый непроверяемый путь `recordProduction`.

`Как иначе:` резерв переводит BLEND на адрес контракта заранее (обычный `transfer`, любой кошелёк). `accrue_epoch` при закрытии считает `assigned` и сравнивает с доступным покрытием; если покрытия нет — начисляет 0 и испускает `StipendUnfunded(epoch, shortfall)` (форфейт, как сейчас у `StipendSkipped`, но без отложенного долга) или начисляет и копит долг — выбор политики, но в одном месте. Claim'ы гейтятся только «эпоха закрыта» (`assigned_at_close_p1 != 0`), не курсором. Удаляются: оба `settleEpochStipend*`, `blend_reserve`, `MAX_SETTLE_CATCHUP`, `STIPEND_FUEL_CAP`, `last_rewarded_epoch_p1`, `StipendLegSkipped`, `StipendSkipped`, `EpochNotAccrued`.

`Поправка 2026-09-04 к формуле покрытия.` Первая редакция этого пункта предлагала считать покрытие как `contract_balance − обязательства` с одним новым полем `unpaid_liabilities`. **Так считать нельзя:** в балансе контракта лежит не только стипендия. `safe_transfer_from` всегда переводит НА адрес контракта (`util.rs:150`), и зовут его четыре места — генезисные стейки спонсора (`initializer.rs:110`), стейк при регистрации (`staking.rs:1066`), каждая делегация (`staking.rs:1157`) и платёж стипендии (`staking.rs:2103`). То есть баланс = забонденный стейк + ожидающие вывода + невостребованные награды + пыль округления (K-9). Вычитание одних лишь стипендиальных обязательств посчитало бы стейк доступной стипендией.

Чтобы формула была верной, нужны три вещи, которых сегодня нет ни одной:
- вызов `balanceOf` — контракт не зовёт его нигде (grep по `src/` вне `tests.rs`: ноль вхождений);
- поле `unpaid_liabilities`;
- **глобальный счётчик забонденного стейка**, поддерживаемый каждым путём делегации, вывода и конфискации. В `StakingStorage` нет ни одного глобального агрегата — только per-validator per-epoch снапшоты (`storage.rs:238-256`).

Третий пункт — основная нераскрытая цена этого упрощения; в первой редакции он отсутствовал. Пока он не построен, курсор `last_rewarded_epoch_p1` остаётся не бухгалтерией, а **гейтом платёжеспособности**: claim физически переводит из баланса контракта (`safe_transfer`, `staking.rs:1675` → `util.rs:182-195`), деньги туда кладёт только `pay_epoch`, и курсор — единственное, что связывает одно с другим. Док `settle_up_to` формулирует это прямо (`staking.rs:2106-2111`).

`Что ломает:` ABI — удаляются 2 селектора + 2 геттера/сеттера резерва, добавляется одно событие; хранилище — 2 поля; узел — не читает ничего из этого (grep). Операционно — резерв должен пополнять контракт, а не давать allowance.

`Что это закрывает:` K-15, K-26, часть T-5. **K-34 НЕ закрывает** (поправка 2026-09-04): якоря K-34 — это `fuel: None` в `safe_transfer_from` (`util.rs:152`), `erc20_transfer_call` (`util.rs:184`) и `external_call` (`consensus.rs:65`), а self-call — единственное место, где кап вообще ПЕРЕДАЁТСЯ (`liveness.rs:498`, `Some(STIPEND_FUEL_CAP)`). Удаление self-call'а убирает единственный site с капом и не трогает ни один из трёх с `None`.

**Принято 2026-09-04 — но НЕ в этой форме.** Выбрана четвёртая: стипендия вообще не входит в
баланс контракта. Резерв остаётся источником и держателем денег, закрытие эпохи только начисляет,
а выплата идёт списанием с резерва ПРЯМО получателю (`erc20_transfer_from_input` уже принимает
произвольного получателя, `util.rs:117-128`). Тогда ни `balanceOf` контракта, ни `unpaid_liabilities`,
ни глобальный счётчик бонда не нужны — проблема смешения не решается, а не возникает. Курсор,
`MAX_SETTLE_CATCHUP`, оба `settleEpochStipend*` и самовызов удаляются так же, как предлагал этот
пункт; политика недофинансирования — форфейт, решаемый при закрытии чтением
`min(balanceOf(резерв), allowance)`. Реализовывать B-3 буквально НЕ нужно; разбор — `DECISIONS.md`,
Д-10, план работ — `PLAN.md` 1.7.

### B-4. Один маршрут слэшинга: системный. Доказательство проверяет узел

`Что сейчас:` три permissionless-селектора по доказательству (`consensus.rs:1166-1203`), парсер (`evidence.rs`, 744 строки), **пять** внешних вызовов верификатора на пути слэша — `compressG2Unchecked` (`consensus.rs:1086`), `compressG1Unchecked` ×2 (`:1117`, `:1122`), `verify` ×2 (`:1132`, `:1146`) — личность по ключу; параллельно системный маршрут по индексу (`:1053-1073`). (Поправка 2026-09-04: прежде здесь стояло «4 внешних вызова» — пересчитано по коду.)

`Чем плохо:` K-1 (верификатор = оружие governance), K-2 (нет привязки к сети/эпохе), K-27 (следствие K-1); два понятия личности (§15.12); 744 строки парсера wire-формата, который «не наш» (`evidence.rs:4-5`) и разъедется с узлом при первом изменении commonware. K-23 из этого списка **снят** 2026-09-04: PAIRING отвергает точку вне кривой, атаки нет — осталась только стилевая хрупкость.

`Как иначе:` удалить три селектора и `evidence.rs`. Оставить `slashEquivocation(epoch, signer_idx)` от `SYSTEM_CALLER`; узел уже проверяет доказательство перед голосованием (`application.rs:709-720`). Если permissionless-репорт нужен (комментарий `consensus.rs:1062-1065` упоминает «epoch-boundary fallback transaction»), то заменить его на **системный** путь с тем же доказательством: узел, получив транзакцию-репорт, проверяет её сам и подаёт `slashEquivocation` — контракту доказательство не нужно. Если всё же оставлять маршрут по доказательству: добавить в namespace идентификатор развёртывания (genesis hash или адрес контракта), требовать `committee_member_at(evidence.epoch, signer) == owner_of(pk)` и `activation_epoch ≤ evidence.epoch` — это закрывает K-2, но не K-1.

`Что ломает:` ABI — 3 селектора; узел — `slasher/actor.rs:1252-1266` формирует именно эти вызовы, нужна правка узла. Верификатор остаётся только для PoP при регистрации — K-1 сужается до «поддельные PoP».

`Что это закрывает:` K-2 и K-27 целиком; K-1 частично (остаётся PoP; для полного закрытия — таймлок на `setBlsVerifier`). K-23 закрывать нечего — гипотеза опровергнута 2026-09-04.
