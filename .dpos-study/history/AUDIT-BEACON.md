## Часть A. Находки

### CRITICAL

**A-1. Эквивокация dealer-лога навсегда лишает share честные узлы, записавшие «не тот» лог; при f byzantine-участниках число честных подписантов seed падает ниже порога, и живучесть seed (а с ней всей цепи) переходит под контроль коалиции.**
- Где:
  - `ceremony.rs:406-422` `record_checked_log` — первый лог dealer'а побеждает навсегда (`recorded.insert` → `false` ⇒ пустой `Step`), ключ — только `PeerPubkey` dealer'а, хэш не участвует.
  - `ceremony.rs:628-646` `ingest_signed_log` — валидный лог того же dealer'а с ДРУГИМ хэшем возвращает `(true, empty)`: fetch помечается выполненным, лог отброшен.
  - `ceremony.rs:870-895` `scoped_pinned_logs` — несовпадение хэша ⇒ `missing`, `all_held=false`.
  - `actor.rs:1993-2012` `fetch_missing_logs` — fetch только для dealer'ов `∉ recorded`; dealer с несовпадающим хэшем уже в `recorded` ⇒ никогда не перезапрашивается.
  - `actor.rs:1470-1487` — `drive_finalization` откладывает с `missing_body` до sweep.
  - `dkg_agree.rs:1346-1353` — `verify` паркуется на `Missing`, `fetch_bodies` доставляет лог, который `ingest_signed_log` отбрасывает (см. выше).
  - `actor.rs:2143-2150` `drive_recompute` — `want = dealers() − held(parse_journal)`, `held` тоже по ключу dealer'а ⇒ `want` пуст при неверном логе в журнале; `actor.rs:2210-2235` — `validate_share_on_poly` ложен ⇒ `adopt=false`, запись остаётся в `recompute_pending` и повторяется каждый тик, пока не постареет.
  - Обнаружение эквивокации логов (две валидные подписи одного dealer'а под разными `DealerLog` для одного `Info`) нигде не выполняется; slasher их не видит (`dkg_agree.rs:1581-1599` reporter не соединён со slasher'ом — по замыслу).
  - Комментарий самого кода признаёт остаток: `actor.rs:1316-1318` «The Byzantine log-equivocation case … still-deferred».
- Сценарий (n=4, один byzantine dealer B): B шлёт `Reveal(L1)` узлу A и `Reveal(L2)` узлам C, D адресно (`Recipients::One`, транспорт это позволяет — честный код шлёт `Recipients::All`, `actor.rs:2437-2445`, но получатель источник рассылки не проверяет). Confirm'ы hash-sensitive (`dkg_agree.rs:201-218`): A подтверждает набор с H(L1), C, D и B — с H(L2). Лидер C пинует H(L2); confirm'ов C+D+B = 3 = quorum ⇒ предложение проходит `rejects_structurally`; A паркует `verify` (Missing) и не голосует, но 3 голосов хватает. Артефакт пинует L2. A: `all_held=false` навсегда, refetch не идёт, recompute зациклен ⇒ A без share на эпоху E и все carry-forward эпохи после неё (heal требует `outcome_at(e)`, а артефакт есть только для E: `actor.rs:2132-2137`). Подписанты seed: C, D, B; порог t = quorum(4) = 3 ⇒ каждый seed требует partial от B. B удерживает partial ⇒ ни одного сертификата (`oracle.rs:227-241`: «NO certificate of this epoch can be assembled») ⇒ остановка цепи до смены комитета, которая сама требует блоков.
- Общий случай: пинуемый набор должен покрываться ≥ quorum confirm'ами ⇒ жертв ≤ n − quorum = f. При f byzantine: честных подписантов 2f+1 − f = f+1 < t = 2f+1. При одном byzantine dealer'е и любом n: честных подписантов n−1−f = 2f = t−1 ⇒ seed-quorum всегда включает byzantine-узел.
- Последствие: нарушение BFT-границы для живучести beacon (f < n/3 достаточно для перманентной остановки), а не «≤ f выпавших».
- Эскиз: (1) `record_checked_log`/`signed_logs` хранить по `(dealer, hash)`, `scoped_pinned_logs` выбирать по хэшу; (2) `fetch_missing_logs`/`fetch_bodies` формировать `want` из `agreed_pinned` по несовпадению хэша, а не по отсутствию dealer'а; (3) `ingest_signed_log` принимать лог с пинованным хэшем даже если dealer уже записан; (4) фиксировать две разные валидные подписи одного dealer'а как evidence (обе `SignedDealerLog` самодостаточны) и как минимум исключать dealer'а из `unsent`/confirm.
- Тег: CRITICAL. Уверенность: код (все звенья прослежены); предположение(порог seed t = quorum(n), `oracle.rs:231` и память `dpos trust root` — совпадает с кодом `bls`, не перечитывалось в этой сессии).

## Итог

Находки по тегам: CRITICAL 1 (A-1), MEDIUM 5 (A-2..A-6), LOW 8 (A-7..A-11, A-13..A-15), NIT 10 (A-12, A-16..A-24); упрощений 12. Плотность: 24 находки / 14,4 тыс. продакшн-строк = 1,67 на тысячу; без NIT — 0,97.

Ответ на исходный вопрос: первый проход по beacon был поверхностным, а не beacon чище. Аргументы: (а) A-1 лежит на центральном пути детерминизма (`record_checked_log` → `scoped_pinned_logs` → `fetch_missing_logs`), проверяется тремя `grep`-ами и прямо назван в комментарии кода как отложенный остаток — первый проход его не поднял; (б) все MEDIUM-находки — расхождения между тем, что код заявляет в комментариях, и тем, что он делает (A-2 «re-agree», A-3 два разных floor'а, A-4 «OsRng»); подсистема на ~45 % состоит из doc-комментариев, и чтение, доверяющее им, систематически недооценивает её; (в) при этом по счёту дефектов на строку beacon действительно не грязнее staking-reader/slasher: 0,97/тыс без NIT (1,67 со всеми тегами) против 4,53 и 2,54 — но там считались все теги. Сопоставимая метрика — «сколько находок CRITICAL/HIGH на подсистему»: у beacon одна CRITICAL с нарушением BFT-границы живучести, чего, судя по постановке, первый проход по beacon не дал вовсе.
