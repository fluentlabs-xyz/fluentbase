## §6 Всплыло

- **`target-contract/` не в `.gitignore`.** `CARGO_TARGET_DIR` создаёт каталог в корне
  дерева, `git check-ignore` его не знает, и `git status` показывает его как untracked.
  Любая следующая сессия, сделавшая `git add -A`, закоммитит несколько гигабайт
  артефактов. В этой сессии `git add` был только по явным путям.
- **`STAKING_ARTEFACT.md` держит третью копию числа 7** (:128, :332). После П2 литерал в

  работы 1.4 это второй проход по уже PENDING валидатору, который тратит лишний переход
  истории видимости (их ровно три, `staking.rs:246-268`). Разобрано в брифе §2 п.3.

  `stamps_are_bounded_per_close_and_by_the_concurrent_budget` (`tests.rs:9057`) утверждает
  «ordered by address» на фикстуре, где порядок адресов совпадает с порядком мест. Класс
  шире одного теста: всякое утверждение о порядке, чья фикстура согласует два порядка, не
  проверяет ни одного из них.
- **`E1-CONTRACT-2.md` §2 П4(в) смешал три вердикта в одном («нет теста»)** для L11, V5,
  V6 — там же, в той же строке, записан механизм, по которому мутация эквивалентна.
  Разобрано в §0 ответе 7; на будущее: вердикт «нет теста» стоит выдавать только после
  попытки построить различающий вход.

## §7 Где проверка слабее всего

1. **Текст мутаций — мой, не исходный** (§3 Д-01). Это самый широкий предел всей работы:
   совпадение имени мутации не доказывает совпадения снятого места, а исходного скрипта в
   репозитории нет.
2. **Три вердикта «эквивалентна» опираются на полноту grep'а по имени аксессора.** Для V5
   я утверждаю, что `staking_token` пишется в одном месте, потому что
   `git grep staking_token_accessor()` дал одну запись; поле, записанное через другой путь
   (сырой слот, макрос), такой grep не увидит. То же для L10 и `readmit_at_epoch_accessor`.
3. **Ворота e2e и `fluentbase-types` до правки не мерены** (§3 Д-06).
4. **Блоб не пересобирался и на стенде ничего не гонялось.** П2 меняет `consts.rs`, то
   есть контрактный крейт; значение константы не изменилось (7 осталось 7), но `.rwasm` в
   `devnet/` собран из прежнего дерева, и что дайджест совпадёт, я не проверял. Смоуки,
   `make case-growth` и `agreement_check.py` в этой сессии не запускались ни разу.
5. **L25 пинит порядок через ПОРЯДОК вектора `pending_exclusion_set`**, то есть через
   порядок пушей в очередь. Если очередь когда-нибудь начнут читать иначе, тест ослабнет
   молча — он утверждает порядок штампов косвенно.
6. **C48 различает мутацию только кодом выхода.** Настоящий отвечает `IntegerOverflow`,
   мутант — `Panic` с кодом точности. Входа, на котором разошлось бы что-то кроме кода,
   не существует (§2 П1), но это значит, что тест пинит код, а не последствие.
7. **Тесты, написанные от состояния, записанного мимо API — два** (`a_queued_validator_…`
   для L10 и частично `an_epoch_with_no_frozen_weight_…` для L13). Оба названы в самом
   тесте комментарием, но оба утверждают поведение на состоянии, которого контракт своими
   путями не производит.
8. **Бриф 1.4 не исполнялся ничем.** Весь его разбор «что будет, если применить
   наполовину» — рассуждение по коду, ни одна из двух веток не собиралась даже в
   черновике. Числа про горизонт коммита (до двух эпох) выведены из
   `MAX_COMMITTEE_LOOKAHEAD_EPOCHS` и `nextEpochToCommit`, а не измерены на стенде.
9. **README сверен по утверждениям, а не по полноте.** Я проверял то, что README говорит;
   я не проверял, чего он НЕ говорит — например, что разделы не пропускают механизма,
   появившегося после их написания.
10. **Формальная вычитка правленых `.md` сделана счётчиками** — строки, обрывающиеся на
    многоточие: 0; строки с нечётным числом обратных кавычек: 0 вне
    ограды кода в README; `,,`: одна, и та внутри кода, описывающего сам счётчик; пустые двойные
    кавычки и пустые скобки вне кода: 0. Смысловой вычитки целиком ни одного файла не
    было.
