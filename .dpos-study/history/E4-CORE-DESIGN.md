## §5. Целевая архитектура

Правило отбора: компонент попадает сюда только со сценарием из §5.6; всё, что «на всякий случай», — в §5.5 «удаляется». Версия после сверки с контр-рецензией (§10): изменения против первой редакции помечены «[изм. §10]».

### 5.1 Модуль комитета — `committee/`

**Запись (значение):**
~~~
pub struct CommitteeRecord {
    pub epoch: u64,
    pub members: Vec<Member>,          // порядок — как вернул контракт (raw byte-lex; check_committee_ordering как сейчас, reader.rs:345-351)
    pub weights: Vec<u128>,            // ОБЯЗАТЕЛЬНЫ — гарантированы инвариантом окна (ниже); weights: None в окне = контракт отдал невозможное

    // производные, один раз из members: bimap: BiMap<PeerPubkey, BlsPubkey>, participants: Set<PeerPubkey>
}
pub struct Member { pub address: Address, pub peer: PeerPubkey, pub bls: BlsPubkey }   // activation_epoch — нет потребителя в ядре, не переносится [изм. §10 A7]; tombstoned — НЕ здесь
~~~
Форма — **Д-1 (а) с уточнением**: запись полностью заморожена, `tombstoned` не входит в запись и живёт отдельным liveness-слоем `TombstoneSet`. Причина по коду: (1) три замороженные ноги и живой флаг — так контракт и возвращает их (`reader.rs:650-710`, `:686-697`); (2) вариант (б) «заморозить флаг в следующей записи» по коду пуст: тумбстоун одновременно снимает статус ACTIVE, ставит JAIL и гасит видимость отбора (`contracts/staking/src/consensus.rs:870-880`), а отбор берёт только `STATUS_ACTIVE ∧ selection_visible_at` (`:508-509`), значит tombstoned-валидатор не попадает ни в одну ПОЗЖЕ коммитуемую запись, и замороженный флаг был бы всегда `false`; следующая коммитуемая запись — `cur+2` (`node/evm.rs:895-902`), то есть «≤ 1 эпоха» из Д-1(б) по коду 2 эпохи, причём без эффекта; (3) потребители флага liveness-only (RULE 37; `application.rs:835`, поллер `node/dpos.rs:1720-1752` [перепинено 1b11b61f]), `is_member` его не читает (`epoch_manager.rs:1106-1111` [перепинено 1b11b61f]) — свойство 1 требует не замораживать флаг, а не читать его из записи; тип это и делает.

**Якорь (единственный).** `committee[E]` закоммичен в состоянии первого блока эпохи `E−2` (`commit_height(E) = start(E−2)`: `drive_ahead_commit` коммитит всё `next ≤ current_epoch + 2` на каждом блоке, `node/evm.rs:895-902`, `current_epoch = epoch_at_block(block_number)` `:1071`, вызов `:1231`) и с этого момента неизменен по составу, ключам и биту; веса живут в кольце `WEIGHT_RING_EPOCHS = 16` (`contracts/staking/src/consts.rs:367`) и после оборота читаются как `None` (`consensus.rs:432-437` → `reader.rs:667-668`). Модуль читает запись на **локально исполненном хэше ordering-финализированного tip'а** узла: `anchor = executed_state_hash(ordering_finalized)`; если `ordering_finalized < commit_height(E)` ⇒ `NotReadable{ready_at: commit_height(E)}` без EVM; иначе один EVM-вызов (плюс `getDkgQual`); пустой ответ ⇒ тоже `NotReadable` (контракт пропускает коммит только вместе с остановкой цепи — E4-25), никогда `Permanent`.

**Инвариант окна (почему веса обязательны и запись одна у всех) [изм. §10 A3/A9/E4-31].** Модуль читает эпоху `E` только в окне `epoch(anchor) − SCHEME_RETENTION_EPOCHS ≤ E ≤ epoch(anchor) + 2`; запрос вне окна — `OutOfWindow` без EVM. Кольцо весов эпохи `E` цело, пока `E > epoch(anchor) + 2 − 16` (самая новая закоммиченная эпоха на якоре — `epoch(anchor)+2`, кадр `E mod 16` перезаписан не раньше `E+16`), то есть при `E > epoch(anchor) − 14`; окно требует `E ≥ epoch(anchor) − 8`; `14 > 8` ⇒ веса присутствуют для любой эпохи, которую модуль вообще читает. Это и делает подвижный якорь безопасным для свойства 1: в окне значение записи (состав, ключи, бит, веса) не зависит от `anchor`, а вне окна модуль не читает. Инвариант пинуется `const_assert!(WEIGHT_RING_EPOCHS − MAX_COMMITTEE_LOOKAHEAD_EPOCHS > SCHEME_RETENTION_EPOCHS)` из общих констант (`staking_protocol`, `consensus/lib.rs:26`). Почему не якорь П-1 «первый финализированный блок ≥ `start(E−2)`» [изм. §10 A9 — отклонено]: (1) чтение на фиксированной старой высоте — до 2 эпох назад — требует исторического состояния, которого ни один сегодняшний путь не читает (все читают `number − K` или `fin`), и его наличие под reth-обрезкой истории не проверено ([ГИПОТЕЗА]); (2) равенство записей между узлами при подвижном якоре доказано выше арифметикой кольца, а не предположением; (3) `NotReadable` покрывает бэкфилл на обоих якорях одинаково.

**Кэш и ретенция [изм. §10 A13].** Одна карта `BTreeMap<u64, EpochEntry{record: Arc<CommitteeRecord>, scheme: Arc<BlsScheme>}>` — запись и её схема живут вместе, одна ретенция `SCHEME_RETENTION_EPOCHS` (`pop_first`, как сегодня `outer.rs:373-375`); `EpochSchemeProvider` становится видом на эту карту. Запись write-once; повторное чтение с другим значением ⇒ `error!` и отказ эпохи (контракт отдал два разных ответа — форк контракта); без `debug_assert` [изм. §10 A14].

### 5.2 Фронтир

**Тип и единственный писатель [изм. §10 A31].** `Frontier { round, height, digest }` — это marshal tip как его несёт `Update::Tip(Round, Height, Digest)` (CW `marshal/mod.rs:131-133`); тело и сертификат прыжок берёт из локального архива marshal'а (`get_finalization(height)`, `get_block`), куда их положил `store_finalization` после `verify_delivered` (CW `core/actor.rs:1404-1463`) — единственный писатель, плюс восстановление tip'а из собственного архива при старте (`:396-401`). Удаляются: `upstream_frontier` (`executor.rs:531-587` [перепинено 1b11b61f], писатели `:1997-2001` [перепинено 1b11b61f], `cert_inlet.rs:646-655` [перепинено 1b11b61f]), `LiveFrontierTee.live_height` (`cert_inlet.rs:318-361` [перепинено 1b11b61f]; `dkg_height_tx` из того же tee ОСТАЁТСЯ до Э5 5.4 — его замена там [изм. §10 B8]), `highest_observed_epoch` + `corroborate_frontier` + `observed_reporters` + `sender_pins` (`epoch_manager.rs:1786-1818` [перепинено 1b11b61f]; per-sender квота пинов для членов не нужна — состояния на отправителя больше нет [изм. §10 B3]), `last_tip_height` как курсор.

**`deliver` — единственная точка доверия [изм. §10 A36/A38/A64/A74].** Ответ на `Latest` или `Finalized{h}` проходит: (1) декод с cap; (2) `Finalized{h}` ⇒ `block.height == h`; (3) `epoch_of(block.height) == round.epoch`; (4) `committee(round.epoch)` из модуля: `Ok` ⇒ BLS 2f+1; `OutOfWindow` ⇒ ответ ОТБРАСЫВАЕТСЯ с метрикой, `deliver` возвращает `true` (fetch закрыт, пир не наказан); `NotReadable` ⇒ то же; (5) BLS прошёл ⇒ `marshal.verify_block` + `report_finalization` — tip двигается. Возврат `false` — ТОЛЬКО на сигнале лжи: недекодируемо, чужая высота на `Finalized{h}`, `epoch_of(height) ≠ round.epoch`, BLS не прошёл под читаемым комитетом. По коду CW `false` = `block!` (no-op при `NoopBlocker`) + `fetcher.block(peer)` ⇒ пир в `excluded` до рестарта движка резолвера, `excluded` никогда не очищается (`resolver/p2p/engine.rs:436-437`, `fetcher.rs:94`, `:242`, `:516`; `reconcile` его не трогает `:500-505`) — это принимается как исход для лжеца, поэтому `false` не отдаётся ни на «не могу проверить», ни на «нет данных» (пир без данных отвечает `Payload::Error` ⇒ `add_retry` без бана, `engine.rs:378`, `:444-456`). Честный пир никогда не отдаёт чужую высоту (`handle_produce` ищет ровно `Finalized{height}`, CW `core/actor.rs:808-818`), так что постоянное исключение по (2)–(4) бьёт только лжеца. Цена: BLS 2f+1 в задаче frontier-резолвера (`engine.rs:426`) — только на FRONTIER-канале, не на marshal-резолвере; частота ограничена пробой.

**Триггер и лестница — один шаг [изм. §10 §0.2(а), §0.3(в), A45, A48, A49, A50, B5, B6; изм. 3-й проход — ступень `last(T+1)` вместо `last(epoch(fin)+2)`].** Marshal tip отставшего узла замерзает по построению (всё выше `epoch(fin)+2` отбрасывается), а `upstream_frontier` удалён — поэтому триггером служит не высота, а **проверенная финализация впереди**: фронтир-проба (`probe_frontier`, `executor.rs:1988-2020` [перепинено 1b11b61f], уже срабатывает по «tip не сдвинулся с прошлого тика», `:1992-1996` [перепинено 1b11b61f]) на каждом тике при замёрзшем tip'е запрашивает `Finalized{last(T+1)}` у `committee(T+1)` (`fetch_targeted`) плюс `Latest` (нецелевой). `T` — эпоха, которую узел последним передал в `track` (`last_tracked_epoch`, = `E` из §5.3): `T = epoch(fin)`, если `fin` не последний блок эпохи, и `T = epoch(fin) + 1`, если последний (`epoch_transition.rs:519-527` cold start; `:543-544`, `:587` граница: `next = epoch_e + 1`). **Почему ступень отправляется.** CW отправляет целевой fetch только пиру из `participants`: `get_eligible_peers` фильтрует `self.participants` по `targets` (`resolver/src/p2p/fetcher.rs:233-245`), при пустом пересечении ключ пропускается со счётчиком `requests_created{Dropped}` (`:278-283`), и следующая попытка откладывается на `Duration::MAX` до смены peer-set'а (`:350-355`); `participants` перезаписывается только из `update.latest.primary` (`resolver/src/p2p/engine.rs:202-205`). Primary по §5.3 = `C[T−1] ∪ C[T] ∪ C[T+1]` — `committee(T+1)` в нём есть, ступень уходит. `committee(T+2)` в primary нет: ступень `last(epoch(fin)+2)` первой редакции с середины эпохи не отправилась бы вовсе (проверка сверки §2(в) — принято по коду; вариант «primary ∪ C[T+2]» отклонён — П-5 не меняется, §6). Шаг по эпохам: с середины эпохи — одна (`last(E+1)` при `T = E`); после посадки на границу `last(T+1)` ET трекает `T+2` (`:543-544`), primary становится `C[T+1] ∪ C[T+2] ∪ C[T+3]`, следующая ступень — `last(T+3)`: две эпохи за посадку. Кто отдаёт: honest marshal отвечает на `Finalized{h}` из своего архива при наличии ПАРЫ (финализация и блок) без проверки членства запросившего (CW `marshal/core/actor.rs:808-818`); `committee(T+1)` выбрано как множество, финализировавшее `last(T+1)`. Локально `committee(T+1)` читаемо (`commit_height(T+1) = start(T−1) ≤ fin`), и `deliver` проверяет ответ под ним. Всё, что вернулось и прошло `deliver`, попадает в marshal ⇒ tip растёт ⇒ обычный триггер `tip − ordering_finalized > threshold` запускает прыжок к tip'у (`threshold = min(JUMP_THRESHOLD, interval)`, `JUMP_THRESHOLD = 1024` `cold_start_jump.rs:77`, `consensus/dpos.rs:2472` [перепинено 1b11b61f], `:3274` [перепинено 1b11b61f]; сравнение `executor.rs:2260-2261` [перепинено 1b11b61f]); первая ступень с середины эпохи даёт `gap ≥ interval + 1 > threshold`, следующие — `2·interval`; при `gap ≤ threshold` — контигуозный догон (`try_repair_gaps` от floor). Неаутентифицированного входа у триггера нет: раздутый `Latest` (R-004) вне окна отбрасывается, внутри окна — проверяется; максимум, что он стоит, — один цикл целевых fetch'ей у комитета, без FCU и без EVM за пределами окна. Лестница = повторение того же шага после посадки (новый `fin` ⇒ новый `T` ⇒ новое окно); автомата `Planning/Stepping` нет [изм. §10 A49/A76], `TooFar` для фронтира не существует (фронтир по построению в окне). Исход «никто из `committee(T+1)` не отдал `Finalized{last(T+1)}`» [изм. §10 A50]: узел не стоит — он продолжает контигуозный догон от floor, проба повторяется каждый тик; это не `Idle → Idle`, а «догон вместо прыжка» с метрикой `frontier_step_unserved`. Условие обслуживаемости ступени (у кого-то из `committee(T+1)` в архиве лежит пара на `last(T+1)`) — ЗАКРЫТО кодом и стендом (проход предусловий, `history/E4-PRECONDITIONS.md` Д3) [изм. предусловия]. (а) Архив marshal'а не прунится вовсе: `SetFloor` зовёт `prune_finalized_archives` (CW `core/actor.rs:698-702`), но fluentbase держит финализации и блоки в `immutable::Archive` (`outer.rs:422-423`, `:439`, `:483`), чей `prune` — no-op (CW `marshal/store.rs:223-226`, `:261-264`); чтения по высоте, которыми `handle_produce` (`core/actor.rs:808-818`) и `plane_upstream::serve` (`plane_upstream.rs:147-166`) отвечают на `Finalized{h}`, — `get_finalization_by_height`/`get_finalized_block` (`:1369-1393`) — floor не смотрят; сам `last_processed_height` двигает каждый ack, не только прыжок, так что «прунинг у прыгнувшего» — не механизм. Ретенция = всё, что узел когда-либо СОХРАНИЛ; не хранится только перепрыгнутое — диапазон выше замёрзшего tip'а до посадки, — и для терминала в таком диапазоне единственный источник пары `seed_boundary_below_floor` (`executor.rs:2310-2365`, требует `boundary_fetch`; в стенде `None`). (б) `last(E)` финализируется ЯВНО: движок E не строит потомка `last(E)` (перепредложение на границе, CW `standard/inline.rs:274-293`), поэтому единственный путь его финализации — сертификат на его собственный digest; `boundary_lookup` (`epoch_manager.rs:1428-1439`) требует только блок (`get_block(last)`), не сертификат — явность держится на simplex, не на гейте. Стенд (оба теста — `testbed/preconditions.rs`): `every_node_serves_the_terminal_pair_of_every_passed_epoch_after_re_jumps` — 4 узла, 5 эпох, узел 3 прыгает дважды (посадки 125 и 157, floor 170 > `last(3)` = 127): у ВСЕХ узлов пара на `last(0..4)`, ни одной высоты «блок без сертификата»; `a_node_more_than_two_epochs_behind_freezes_its_marshal_at_the_ceiling_and_jumps_over_a_hole` — гейт 80: узел 3 стоит на 95, его marshal замерзает ровно на `last(epoch(95)+2)` = 159, прыжок 95 → 180 через дыру 160..177 (ничего) и 178..182 (блок без сертификата — обратный parent-walk от потреблённого сертификата 183), терминалы вне дыры есть у всех. Лестница стартует как написана: `committee(T+1)` финализировало `last(T+1)` само и хранит пару без срока; открытым остаётся только терминал ВНУТРИ дыры прыгнувшего узла (сидирование `boundary_fetch`), а такой узел не тот, кому ступень адресована.

**Порядок «аутентификация до `sync_to`».** `cold_start_jump` получает `Frontier` (tip) и достаёт из архива `(finalization, block)`; need-gate ⇒ `sync_to(block.result)` ⇒ после `Valid`: `block_hash(landing) == block.result` (посадка — заверенная ветка), `Landed{floor}`; `verify_jump_structural`/`verify_jump_authenticated` как стадии удаляются (структура проверена marshal'ом при `handle_deliver`, `core/actor.rs:987-993`; BLS — в `deliver`). **`sync_to` — единственный писатель EL-тегов на этом пути (`cold_start_jump.rs:478-482`), и это не меняется; меняется только его вход.** L1: `holds(l1)` остаётся для follower'а с `--dpos.l1-checkpoint`, исход `holds == false` остаётся `JumpOutcome::L1Fork ⇒ SafetyHalt` (`cold_start_jump.rs:848-857`), ошибка самой L1-пробы ⇒ `Stalled` (повтор) вместо сегодняшнего `AuthFailed` (`:860-861`) [изм. §10 A47/A51/B16/B17].

**Правило единое, без исключения по типу datadir [изм. §10 A46, E4-30].** `sync_to` вызывается только с проверенным `Frontier`. Три сегодняшних входа: прыжок (`cold_start_jump.rs:839`, три вызывающих), follower на существующем datadir (`consensus/dpos.rs:3008` [перепинено 1b11b61f]: `up.get_latest()` ⇒ `el.sync_to` без единой проверки), follower на свежем datadir (`:3052` [перепинено 1b11b61f], `activation = 0`, до геометрии). Первые два идут через `Frontier` (у follower'а с datadir геометрия и модуль читаются локально на `rf_hash`). **[ДОПОЛНЕНО 2026-09-13, Э5 строка 4.4, отклонение `4.4а-Д-10`.]** «Три входа» и «первые два через `Frontier`» — счёт и маршрут на момент письма, не инвариант. Абзац про `:514` («`sync_to` — единственный писатель EL-тегов на этом пути, и это не меняется; меняется только его вход») строкой 4.4 НЕ затронут и соблюдён дословно: писатель остался один, поменялся ровно вход. **Диаграмма состояний прыжка (целевая) [изм. §10]:**
~~~
Idle ──(tip не сдвинулся с прошлого тика)──▶ Probing: fetch_targeted Finalized{last(T+1)} у committee(T+1) ⊂ primary; fetch Latest   (T = last_tracked_epoch)

Probing ──ничего не прошло──▶ Idle (контигуозный догон от floor продолжается; метрика)

Syncing ──reth Invalid──▶ InvalidTarget (тот же исход)
Syncing ──no peers 90 s / 6 h──▶ Stalled ──▶ Idle (re-arm)
Syncing ──peers>0, head стоит 300 s──▶ StalledWithPeers ──▶ Idle (re-arm)
Landed ──l1 задан ∧ holds=false──▶ L1Fork ──▶ SafetyHalt ; holds=Err ──▶ Stalled

### 5.3 Граница p2p

**`TrackedPeers`:** `track(E, TrackedPeers{ primary: C[E−1] ∪ C[E] ∪ C[E+1], secondary: registry(at anchor) })` из записей модуля. `E` — эпоха, переданная в `track` (`last_tracked_epoch`): на последнем блоке эпохи `E` трекается `E+1` (`epoch_transition.rs:543-544`, `:587`), при cold start на границе — тоже (`:519-527`); в §5.2 она обозначена `T` [изм. 3-й проход]. Primary НЕ расширяется до `C[E+2]`: ступень лестницы целится в `C[E+1]`, который здесь уже есть (§5.2). По коду CW: реестр (secondary) подключается входящим (`record.rs:341-348`), не набирается исходящим (`:170-173`, `:258-266`), получает ответы резолвера и marshal'а (`resolver/p2p/engine.rs:397-412`), НЕ хранится в `buffered` (`engine.rs:321-323`, `:366-377`), НЕ выбирается для fetch (`:202-205`) — «не отдаёт» потому, что не попадает в `fetcher.participants`, а не потому, что его не спрашивают [изм. §10 §0.8]; secondary не проверяется на `max_peer_set_size` (`tracker/actor.rs:157-164`). Уточнение [изм. §10 A63]: ожидающие `subscribe` в `buffered` будятся ДО фильтра (`engine.rs:313-318`) — secondary может доставить тело подписчику по дайджесту (безопасно, дайджест назван подписчиком), но это доставка до проверки членства — M11 в §2.3. **Смена подписи [изм. §10 §0.6/C.3]:** `PeerSetSink::track(epoch, Set<PeerPubkey>)` (`epoch_transition.rs:129-131`, `p2p/lib.rs:306`, `stand.rs:804-809` [перепинено 1b11b61f]) меняется на `TrackedPeers` ОДНИМ коммитом в 4.3 сразу в четырёх местах: трейт и вызов в `staking-reader` (`epoch_transition.rs:647`), `OracleHandle` в `p2p`, `TrackSink` стенда, стенд `Network::track`; 4.1 подпись не трогает (компилируется на границе 4.1/4.3).

**`Ingress` — тип на входе каждого канала:**
~~~
pub enum Ingress<'a> { Member { peer: &'a PeerPubkey, epochs: EpochMask }, Tracked(&'a PeerPubkey), Dropped }
// классификация без EVM: по TrackedPeers текущего окна (primary ⇒ Member с маской эпох, в чьих записях он состоит; secondary ⇒ Tracked); tombstoned ⇒ Dropped до декода (соединение при этом уже рвёт OracleHandle::block, §5.1)
~~~
Правила по каналам: BEACON/DKG — `Member` для `ceremony_epoch` кадра ДО декода тела; `Confirm.target_epoch ∉ [now, now+2]` ⇒ drop до `committee()` (окно модуля = тот же предикат); EVIDENCE — `Member` в маске ∧ эпоха в окне; VOTE/CERT backup — `Member`, иначе drop (E4-04; `handle_msg_for_unregistered_epoch` без корроборации: член ⇒ `pipeline_catchup_span` только для эпох в окне модуля, EVM только через модуль); FRONTIER/MARSHAL/RESOLVER — запросы обслуживаются и `Tracked`, ответы принимаются только от primary (CW); BROADCAST — CW retain только primary; квоты как есть.

**Штрафа по каналу нет [изм. §10 §0.2(б), A38, A64, A73].** На резолверных каналах событие `deliver == false` уже означает постоянное исключение пира (см. §5.2) — своего счётчика поверх него не заводить; на BEACON/EVIDENCE/backup — `Ingress` + квота, без счётчиков и без таймеров. `NoopBlocker` остаётся на транспорте (PLAN §8 п.1); глобальный бан — только tombstone.

**`deque_size` и бюджет тел:** BROADCAST `deque_size = 4` + байтовый лимит на пира `4 × MAX_ORDER_BLOCK_SIZE`; DKG bodies: `deque_size = 2` — замер (проход предусловий, Д5): ровно 1 отличное тело на (инстанс, отправитель) у каждого узла в B1, B2/C9 (три минта), B3 (отсутствующий дилер) и при разрезе сети `[0,1] | [2,3]` на 6 view внутри окна согласования эпохи 1 (`testbed::preconditions::dkg_bodies_per_peer_are_measured_under_a_partition_in_the_agreement_window`; счётчик — `fakes::BodyTap` на приёмнике BROADCAST, тела различаются по keccak); `Plan::Forward` пересылает тот же digest, который deque не растит (CW `buffered/engine.rs:331-337`); +1 запас на перепредложение после nullify, в замерах не встретившееся [изм. предусловия]; оба — primary только (CW). Декод до проверки — граница библиотеки, принять.

### 5.6 Сценарий, оправдывающий каждый компонент

- `CommitteeRecord` write-once + один якорь + инвариант окна: смена состава между эпохами; догоняющий валидатор читает `C[E+1]` до конца E; два узла на разных высотах — одно значение (класс R-075); кольцо весов не влияет в окне (E4-31).
- `NotReadable` без EVM: границы в первые K блоков после старта (`epoch_transition.rs:391-426`), бэкфилл (R-123).
- `OutOfWindow` без EVM: `on_confirm` с произвольной эпохой (R-023), ответ `Latest` далеко впереди.
- `TombstoneSet` + `OracleHandle::block`: эквивокатор в текущем комитете — отказ лидеру и разрыв соединения, финальность не трогается (RULE 37).
- `Frontier` = marshal tip, `deliver` как единственная точка доверия: R-004, R-009, R-003, R-001.
- Проба ступеней `Finalized{last(T+1)}` у `committee(T+1) ⊂ primary`: отставший узел с замёрзшим tip'ом (B6 критики) стартует лестницу без неаутентифицированного входа.
- Checkpoint только для свежего datadir вне devnet: E4-05; follower с datadir — через `Frontier` (E4-30).
- `L1Fork ⇒ SafetyHalt`: follower с checkpoint при подписанной ветке вне L1-финальности (св. 6).
- `Ingress::Member` из маски без EVM: BEACON/EVIDENCE/backup — M1, M4, M5.
- Secondary = реестр: joiner получает сертификаты и артефакты, не может заполнить буферы (R-013, R-037, Gap-C `09:1095-1106`).
- `deque_size = 4`: R-013 при n = 51.
- Один `EpochTransition`: E4-20 (стенд считает `tracked_mismatches`, `stand.rs:794-797` [перепинено 1b11b61f]).
Не включено (нет сценария): f+1 корроборация; «живой фронтир» для чтения комитета (якорь модуля уже на локальном ordering-tip); второй `CertInlet.schemes`; watchdog; таймерный бан; свой штраф по каналу (событие уже исключает пира в CW); автомат `Planning/Stepping`; `TooFar` для фронтира; `Member.activation_epoch`.
