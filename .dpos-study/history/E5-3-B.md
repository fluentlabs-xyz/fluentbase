### 0.3 Семантика локального бана — как реализовано

- Триггер: `insert_log` возвращает `Equivocation{first}` когда для дилера уже есть `first_log` и приходит check-валидное тело с другим хэшем (`ceremony.rs:496-509`). Создаётся `equivocations[pk] = {first, second}` — ОДИН раз на (эпоха, дилер); третье и далее тело — `Another` (`:511`).
- Бан = только gossip-ingress: `handle(Reveal)` от дилера из `equivocations` → `Step::default()` (`:467`). Резолверный путь `ingest_signed_log` бан НЕ применяет — он принимает ровно то тело `(dealer, hash)`, которое запросили (`:783-800`); replay тоже не применяет (`:850-902`).
- Пришпиленный лог банённого дилера — ПРИНЯТ: узел, держащий только «другое» тело, просит `(e, D, pinned_hash)` (`actor.rs:2271`), сервер отдаёт точно его (`:2753`), `ingest_signed_log` записывает, финализация идёт по `scoped_pinned_logs` с точным id (`ceremony.rs:1053`). Пин проверен стендом: жертва финализирует (`dkg_ceremony_ok=1`, ниже) и юнитом `a_dealers_second_valid_log_…` (`ceremony.rs:2295`).
- Что этот узел предлагает/подтверждает за seat дилера — ПЕРВЫЙ записанный хэш (`first_log`, `signed_log_hash` `:1016`); индекс `recorded_dkg_logs` остаётся first-wins по seat (`actor.rs:1506`), поэтому `ShareConfirm` жертвы по-прежнему называет подложный хэш — свидетель стенда сохранён.
- Evidence в RAM — у ceremony (`equivocations`), живёт до finalize (ceremony удаляется из `ceremonies` при Ok, `actor.rs:1733-1737`) или sweep; в журнале — `DealerEquivocation(first, second)` до `evict_journal` на sweep. Вторая половина пары пишется ТОЛЬКО внутри записи-evidence (`ceremony.rs:537-540`) — журнал без записи не держит ни тела, ни бана (M3).
- Он-чейн ничего (Д-6 defer). Метрика + WARN: `actor.rs:1612-1632`.
- Kворум и пришпиливание не трогались — СТОП по постановке не потребовался.

### 0.4 Оба лога дилера не совпадают с пришпиленным (третий хэш C)

`scoped_pinned_logs` сообщает seat как `Missing` (`ceremony.rs:1053-1063`); `pinned_ready` → `all_held=false` → deferral `missing_body`; `fetch_missing_logs` каждый тик просит `(e, D, C)` у ростера (`actor.rs:2271-2281`); держатель C отдаёт ровно C; `ingest_signed_log((D, C))` принимает (бан не применяется), `insert_log` → `Another` → журнал `PeerLog(C)` (`ceremony.rs:511`, `:533`); evidence остаётся первой парой (A,B); финализация по C. Проверено юнитом: третье тело по gossip — drop, то же тело по точному id — принято, `equivocation()` не меняется (`ceremony.rs:2364-2392`). Если C никто не держит — deferral навсегда (прежняя семантика «ждать, не финализировать подмножеством»); для честно сертифицированного набора недостижимо: лидер держал C и его кворум подтвердил.

Было: `u64_be(epoch) ‖ dealer(32)` = 40 байт. Стало: `u64_be(epoch) ‖ dealer(32) ‖ hash(32)` = 72 байта, `encode_size` = 72 (`log_resolver.rs:85-105`). Кодек-тест: `dkg_log_key_round_trips_and_orders_by_epoch_then_dealer` (`:613-660`) — длина 72, байтовые срезы на местах, round-trip, обрезка до 71 байта не декодируется, два ключа, различающиеся только хэшем, — разные (Eq, bytes, Ord). Сети переподнимаются с генезиса — окна смешанных версий нет (доки: 12 таблица констант).

### 0.6 Replay — чем доказано равенство до/после

`a_replayed_journal_rebuilds_the_recorded_set_and_the_equivocation_pair` (`ceremony.rs:2436-2500`): live-ceremony узла 0 (4 лога) получает второй валидный лог узла 1 по gossip (пара создана, `step.journal = [DealerEquivocation]`); журнал узла 0 = его записи + запись evidence; `resume` → `signed_logs.keys()` ДО == ПОСЛЕ (5 id, оба тела дилера 1), `first_log` ==, `equivocation(d1) == Some({h1, h2})`, `own_log_recorded`, третье тело по gossip после рестарта — по-прежнему drop. Механизм: replay идёт через тот же `insert_log` (`:850-902`) — одна семантика вместо live first-wins / replay last-wins. M3 (без записи) — красный; M3′ (второе тело как PeerLog вместо пары) — replay-тест ЗЕЛЁНЫЙ (пара пересобирается из двух PeerLog тем же правилом), красным становится только shape-assert в `a_dealers_second_valid_log_…` `:2338-2342` — это свойство «одной семантики», не дыра.
