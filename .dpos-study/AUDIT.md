### A1. Безопасность консенсуса и синхронизации

**A-1. Cold-start/re-jump синхронизирует reth к неаутентифицированному хэшу до BLS-проверки, а комитет для проверки читает из уже подменённого состояния.**
- Где: `crates/dpos/consensus/src/cold_start_jump.rs:805-847` (порядок: `get_latest` → `verify_jump_structural` → `el.sync_to` → `verify_jump_authenticated`), `:438-474` (`sync_to` шлёт FCU с `head=safe=finalized=latest.block.result`), `:662-683` (комитет читается при `landing_hash`, полученном из `sync_to`). Валидатор: `dpos.rs:1795-1878` (cold start), `:2458-2553` (`re_jump` с порогом `min(1024, interval)`), `executor.rs:1904-1934` (`probe_frontier` поднимает `upstream_frontier` по ответу любого пира), `:2160-2207` (`maybe_re_jump`). Транспорт: `plane_upstream.rs:270-310` (`FrontierKey::Latest` отвечает любой отслеживаемый пир, ответ не подписан).
- Инвариант: 5 (`result` = EVM-хэш) и корень доверия к комитету; сам инвариант «reth следует только за BFT-финализированной цепью» в §4 отсутствует.
- Сценарий: любой пир из tracked-набора (реестр ∪ комитеты, до 4096) отвечает на `FrontierKey::Latest` пару `(cert, block)` с `payload == block.digest()` и `block.result = H_attacker`, `block.height > ordering_finalized + threshold`. Узел вызывает `sync_to`: reth получает FCU с `finalized_block_hash = H_attacker`, скачивает по devp2p ветку атакующего (EL проверяет только исполнение, не консенсус), канонизирует и финализирует её. Затем `verify_jump_authenticated` читает `committee[E]` при `landing_hash` — из состояния атакующего, где записаны его ключи — и проверка проходит. `JumpOutcome::Landed` → `reseed_forward` → узел живёт на чужой цепи. Для follower без `--dpos.l1-checkpoint` то же самое. Даже при провале аутентификации reth уже финализировал чужой хэш, а обратный FCU reth отклоняет (`dpos-reth-skips-backward-fcu`).
- Последствие: захват отставшего узла (или здорового, которого заставили «отстать» через ложный frontier); RPC отдаёт чужое состояние; валидатор перестаёт участвовать.
- Эскиз: аутентифицировать `latest` ДО `sync_to` по комитету, прочитанному из ЛОКАЛЬНОГО финализированного состояния (ограничивает прыжок окном `SCHEME_RETENTION_EPOCHS`); дальше — только по явному weak-subjectivity checkpoint (см. B-5). `probe_frontier` не должен поднимать `upstream_frontier` без проверенного сертификата.
- Тег: **CRITICAL** (подтверждено).
- Уверенность: код + эксперимент.
- Проверка 2026-09-03 (devnet `devnet/local-dpos-smoke`, образ `fluent-dpos-smoke:local`, фаза 1; `engine_forkchoiceUpdatedV3` через authrpc контейнера с JWT из `jwt.hex`):
  1. FCU на validator-1 с `head=safe=finalized=0x11…11` (хэша нет ни у кого): ответ `{"status":"SYNCING","latestValidHash":null}`; `eth_getBlockByNumber("finalized")` не изменился (0x40); узел продолжил принимать свои FCU; в логе `Received forkchoice updated message when syncing`.
  2. FCU с известным каноническим `head` и неизвестным `finalized=0x22…22`: ошибка `-38002 Invalid forkchoice state`; finalized не изменился. То есть защита `finalized` действует только когда `head` известен.
  3. Отдельный узел `fluent node` без консенсусного драйвера (genesis, один devp2p-пир validator-0) получил FCU `head=safe=finalized=H`, где `H` — блок 0x40 validator-0, локально отсутствующий: первый ответ `SYNCING`, через 4 с pipeline-backfill (`Headers … Finish`, 13 стадий, `target=64`) и второй тот же FCU — `VALID, latestValidHash=H`, `finalized = 0x40/H`. reth финализировал хэш, который ему назвали, получив блок по devp2p; ни одной консенсусной проверки в этом пути нет.
  Код reth (`~/.cargo/git/checkouts/reth-9084db4313ec21c5/8cc96a3/crates/engine/tree/src/tree/mod.rs`): диспетчер `:1117-1147`; неизвестный head ⇒ `handle_missing_block` `:1320-1348` (SYNCING + `DownloadRequest::single_block`, safe/finalized не проверяются); скачанный блок = sync target ⇒ `MakeCanonical`/`make_canonical` `:2740-2770`; следующий FCU с head == canonical tip ⇒ `ensure_consistent_forkchoice_state` `:1188-1215` ⇒ `update_finalized_block` `:3106-3126` ставит finalized на любой известный канонический хэш; `InsertExecutedBlock` не канонизирует `:1551-1576`.
  Ответы на три вопроса: принимает — да (SYNCING, без ошибки); в SYNCING переходит и запускает скачивание/backfill; finalized-указатель не трогается пока блок неизвестен и переезжает на названный хэш сразу после того, как блок получен по devp2p и повторён FCU. Предусловие атаки: атакующий должен уметь отдать блок жертве по devp2p (в devnet `--trusted-only` это закрывает; продовая конфигурация devp2p не входит в `crates/dpos`). Осталось непроверенным эмпирически: принимает ли pipeline ветку, форкающуюся ниже локального finalized (часть D, п. 2).

**A-2. `verify_block` не проверяет `fee_recipient`.**
- Где: `application.rs:496-509` (`structural_checks`), `:817-1010` (`verify_block`); поле `order_block.rs:104`.
- Инвариант: не покрыт §4 (там нет правила для `fee_recipient`).
- Сценарий: лидер ставит в `fee_recipient` любой адрес; все верификаторы голосуют «да»; deriver (в `crates/node`) исполняет блок с этим получателем.
- Последствие: любой лидер присваивает комиссии любого блока.
- Эскиз: сверять `block.fee_recipient` с адресом, привязанным к `ctx.leader` в снапшоте комитета (нужен маппинг peer→address в `ValidatorSetSnapshot`, он уже есть).
- Тег: **HIGH**. Уверенность: код.

**A-3. `verify_certificate` при `SeedCheck::NoKey` принимает любой σ; follower с ещё не полученным `PK_E` кладёт подделанный сертификат в архив и виснет.**
- Где: `bls/src/combined_scheme.rs:428-444`; `cert_inlet.rs:690` (`ensure_key` только `Local`), `:824-863` (verify → `capture_certificate_seed` → `quarantine`), `:917-930` (сертификат уходит в marshal); `executor.rs:1764-1794` (hold `awaiting_seed`), `:2845-2871` (только лог через 60 с); промоушен `certify.rs:288-327` роняет Invalid.
- Инвариант: 4 (в beacon-active эпохе сертификат несёт корректный σ).
- Сценарий: upstream (или пир по FRONTIER) отдаёт валидный multisig-сертификат с изменённым слотом σ, пока у follower нет `PK_E`. Сертификат проходит, блок доставлен, σ в карантине. Когда ключ приходит, σ отброшен как Invalid; `seed_for(round)` = None навсегда; executor держит блок и все последующие. `record_data_fault` не вызывается (verify прошёл) — ротации upstream нет. Архив финализаций теперь содержит сертификат с плохим σ и отдаёт его другим узлам, которые видят data fault и ротируют ОТ честного follower.
- Последствие: остановка follower до ручного вмешательства; отравление архива.
- Эскиз: не принимать сертификат beacon-active эпохи без ключа (fail-closed; ключ получать через `PinEffort::Thorough` до verify), либо хранить сертификат отдельно от «принят в архив» до проверки σ. Общий вариант — B-1.
- Тег: **HIGH**. Уверенность: код.
- Проверка: путь до marshal (`cert_inlet.rs:824-930`) и отсутствие data fault при прошедшем verify — код; остаточное предположение только о том, ротирует ли оператор upstream вручную.

**A-4. σ финализированного блока записывается только из `Activity::Notarization` и из backfill через `UpstreamResolver`; финализация без локально виденной нотаризации оставляет executor без σ навсегда.**
- Где: `spec_exec.rs:52` (`let Activity::Notarization(n) = activity else { return }`); полный список точек захвата: `spec_exec.rs:99,107`, `cert_inlet.rs:863,3152`, `beacon/follower.rs` (тесты). `outer.rs:1426-1500`: без `upstream` резолвер marshal — `Plane`, захвата σ нет. `executor.rs:1764-1794` держит блок; `:2845-2871` только предупреждение; гейт `:1388-1411` останавливает все финализации.
- Инвариант: 10 (ack не теряется) соблюдён, но ценой вечной остановки.
- Сценарий: узел получает `Certificate::Finalization` вида, для которого нотаризацию не собрал и не получил (пропущенный пакет, view прошёл во время догоняния; CW сообщает `Finalization` в `voter/actor.rs:653` независимо). Marshal доставляет блок, `seed_for(Round(E, v))` = None. Никакой источник σ для этого раунда больше не сработает: сертификат финализации содержит тот же σ, но его никто не извлёк.
- Последствие: остановка исполнения на валидаторе; ordering-плоскость уходит вперёд (≤ 2 эпох по `dpos-ordering-plane-two-epoch-liveness-ceiling`), затем узел выпадает.
- Эскиз: извлекать σ из ЛЮБОГО сертификата (Notarization и Finalization) в одном месте — в Reporter-цепочке marshal (B-1); в executor — при `Missing` читать сертификат из `finalizations_by_height` marshal.
- Тег: **HIGH**. Уверенность: код (обе половины).
- Проверка по commonware (`CW/consensus/src/simplex/actors/`): сетевой `Certificate::Finalization` обрабатывается независимо от нотаризации — `voter/actor.rs:1026-1032` → `handle_finalization` `:454-462` только сохраняет сертификат (`round.rs:421-436`); `Activity::Finalization` сообщается из `broadcast_finalization` (`round.rs:462-471`, `voter/actor.rs:630-654`), `Activity::Notarization` — только при наличии собственного `round.notarization` (`round.rs:438-447`). Батчер не строит сертификаты для view ≤ finalized (`batcher/actor.rs:568`), т.е. догоняющий узел получает финализации для view, нотаризацию которых он не собирал и не получал, штатно. Частота на живой сети — часть D.

**A-5. Ложный frontier от f+1 любых tracked-пиров переводит валидатор в verify-only навсегда.**
- Где: `epoch_manager.rs:1694-1726` (`corroborate_frontier`: порог `(n−1)/3+1`, отправитель — любой аутентифицированный пир), `:947-949` (`is_live_epoch = epoch >= highest_observed_epoch`), `:1006-1011` (не live ⇒ только `soft_enter`); источник `their_epoch` — id сабканала кадра без подписи (`crates/node/src/dpos.rs:1137-1152`).
- Инвариант: не покрыт; фактический инвариант «highest_observed_epoch ≤ реальная эпоха сети» ничем не защищён.
- Сценарий: два пира из реестра (не из комитета, n=4 ⇒ порог 2) шлют по кадру на VOTE-сабканал `10^9`. `highest_observed_epoch = 10^9`; каждая настоящая граница `E` считается «не live», `reconcile_roles` делает `soft_enter` и выходит. Значение никогда не убывает.
- Последствие: узел не спавнит движки до рестарта; при n=4 достаточно двух коллюдирующих стейкеров вне комитета, чтобы вывести любого валидатора.
- Эскиз: считать frontier только по проверенным сертификатам (финализация эпохи e под `scheme(e)`) — то, что marshal и так делает; удалить `observed_reporters`/`sender_pins` (B-4). Минимум — ограничить отправителей `committee[highest_entered]`.
- Тег: **HIGH**. Уверенность: код.
- Проверка цепочки: соединения устанавливаются только с пирами из отслеживаемых наборов (`CW/p2p/src/authenticated/discovery/actors/tracker/directory.rs:444-446` `eligible`, `:521-530` `reserve`; `spawner/actor.rs:138`); отслеживаемый набор эпохи = реестр ∪ `committee[e]` ∪ `committee[e+1]` (`epoch_transition.rs:614-648`), хранятся последние 4 набора (`tracked_peer_sets` по умолчанию, `p2p/src/config.rs:98`). Кадр с незарегистрированного сабканала попадает в backup без фильтра по членству (`crates/node/src/dpos.rs:1137-1152` — только `epoch_from_subchannel`), дальше `epoch_manager.rs:729-745` → `:889-930` → `:1694-1726`. Порог считается по `committee_size` текущей вошедшей эпохи, пины — 2 эпохи на отправителя (`:398`). Путь ровно такой, как записано: f+1 различных пиров из реестра или недавних комитетов.

**A-6. Guard #2 сравнивает attested result с канонической цепью reth ДО FCU, который канонизировал бы только что выведенный блок; при спекулятивном сиблинге на той же высоте — ложный SafetyHalt.**
- Где: `executor.rs:3131-3152` (guard #2 читает `spec_executed_hash(height)`), выполняется после `derive_finalized_with_gap_fill` (`:3039-3041`), который для целевого блока делает только `submit_finalized_payload` и выходит без FCU (`:3635-3645`); FCU целевого блока — позже, `:3289`. `spec_executed_hash` = `provider.block_hash(height)` — каноническая цепь (`crates/node/src/ordering.rs:45-47`). Спекулятивный блок канонизируется FCU `head=derived` в `spec_execute` (`:2684-2732`). reth: `InsertExecutedBlock` не меняет канонической цепи (`reth …/engine/tree/src/tree/mod.rs:1551-1576`).
- Инвариант: 5, 9.
- Сценарий: view v нотаризован блоком X на высоте h, узел спекулятивно исполнил X (`SpecNotarized`) и FCU'нул его как head. View v нуллифицирован, следующий лидер предлагает Y на той же высоте h, Y финализирован. Узел отстал ≥ K блоков (`last_tip ≥ h+K`). `try_derive(Y)`: `correctly_speculated = false`; derive+import Y без FCU; guard #2 читает `block_hash(h)` = X ≠ hash(Y) = attested result в блоке h+K ⇒ `Some(false)` ⇒ `Fault::fork_safety(ResultDivergence)` ⇒ SafetyHalt.
- Последствие: честный узел защёлкивается навсегда при штатной комбинации «таймаут лидера + отставание на K».
- Эскиз: сравнивать с `derived_hash` (уже вычислен), а не с канонической цепью; либо выполнять guard #2 после FCU целевого блока. Отделять «EL не переключился» от «EL держит другой блок ниже finalized».
- Тег: **HIGH** (повышено с MEDIUM: порядок и семантика подтверждены кодом; сценарий — штатный).
- Уверенность: порядок вызовов, семантика `spec_executed_hash` и поведение `InsertExecutedBlock` — код; частота «нотаризован → нуллифицирован → другой блок на той же высоте при отставании ≥ K» — эмпирика (часть D).

**A-7. Цикл повторного применения в `try_derive` не ограничен, если EL не канонизирует производный блок выше finalized.**

### A2. Границы эпох

**A-11. Геометрия эпох заморожена на первом чтении; изменение `epochBlockInterval`/`dposActivationBlock` в контракте расколет сеть между перезапущенными и работающими узлами.**
- Где: `staking-reader/src/epoch_transition.rs:44-65, 465-483`; `dpos.rs:1651-1654` (валидатор читает при `cs_finalized_hash` на старте); `reader.rs:488-494` (комментарий утверждает отсутствие кэша — не соответствует поведению `EpochTransition`).
- Инвариант: 16 (заморозка) и предположение §12.X «неизменность — ВЕРА».
- Сценарий: governance меняет interval; узлы, стартовавшие после, считают эпохи по-новому; работающие — по-старому. `OriginEpocher`, `is_epoch_boundary`, партиции `consensus_epoch_{E}` и сабканалы расходятся.

## Часть C. План приведения в production

Порядок диктуется тремя зависимостями: во-первых, ничто в executor и beacon нельзя менять, пока сид приходит по четырём путям, потому что каждая правка исполнения должна доказываться на одном источнике σ; во-вторых, любое изменение wire-формата (B-3) — координированный релиз всей сети, и его надо совместить с другими несовместимыми изменениями; в-третьих, стенд с несколькими узлами нужен раньше рефакторинга executor, иначе B-8 не проверяем.

Первый этап закрывает то, что эксплуатировать удалённо: A-1 вместе с B-5 (аутентификация до синхронизации; до появления тулинга checkpoint временно запретить прыжок за пределы окна `SCHEME_RETENTION_EPOCHS`), A-5 вместе с B-4 (frontier только по сертификатам), A-2 (проверка `fee_recipient`), A-12 (читать `getDkgQual` в `maybe_start` и хранить все минты окна на диске — это требует согласования с контрактом и должно идти вместе с кросс-репо тестом), A-40 (либо доказательство PoP в контракте тестом, либо проверка на узле). Эти пять работ независимы друг от друга и могут идти параллельно; ни одна не меняет wire-формат.

Второй этап — живучесть исполнения: B-1 (единый вход σ), закрывающий A-3, A-4, A-20, A-13; следом A-7 (ограничить цикл re-apply) и A-6 (уточнить вердикт ForkSafety). B-1 обязан идти до любого рефакторинга executor, потому что после него executor читает σ из одного места и половина его ветвей исчезает сама. Параллельно с B-1 можно делать слэшер: A-35, A-36, A-22 и решение по B-3 (только решение и контрактную часть; удаление поля из блока — в третьем этапе).

Третий этап — один координированный несовместимый релиз: удаление `equivocation`/`accused` из `OrderBlock`, если выбран вариант «убрать» в B-3, плюс перенос протокольных констант в chainspec (B-9). Оба меняют то, о чём сеть должна договориться байт-в-байт, поэтому их надо выпускать одним обновлением всех валидаторов с остановкой на границе эпохи. До этого релиза не имеет смысла трогать тесты conformance для `extra_data`.

Четвёртый этап — упрощение без изменения поведения сети: B-2 (один лончер), B-6 (один `Randomness`), B-7 (два хранилища beacon), B-10 (убрать `Option`), B-11 (типизированные ошибки reth). Эти работы зависят только от того, что B-1 уже сделан (иначе B-6/B-7 переписывать дважды). B-2 и B-6 можно делать параллельно, B-7 — после B-6.

Пятый этап — B-8 (разделение executor) и ресурсные ограничения A-28, A-36, A-44, A-45. B-8 не имеет смысла раньше B-1 и раньше стенда, на котором проверяются сценарии раздела D.

Работы, после которых система временно менее безопасна, чем до начала: B-3 в варианте «убрать» — между обновлением первого и последнего валидатора сеть не имеет кворума (несовместимые digest), а до появления контрактного пути слэша через WAL-транзакцию (он есть) наказание задерживается на эпоху; B-7 — узел, обновлённый посреди эпохи, стартует без ключевого журнала и до подтягивания артефактов находится в vote-only admission; B-5 в части запрета прыжка за окно — узлы, отставшие больше окна до появления checkpoint-тулинга, не догоняют автоматически; B-1 — в момент выкладки на follower оба пути записи σ работают параллельно, и любая ошибка в новом пути даёт форк derive у follower (валидаторов не затрагивает, если менять сначала follower).
