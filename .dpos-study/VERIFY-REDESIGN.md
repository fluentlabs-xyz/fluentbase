## Часть 3. Три крупнейших предложения

### П-1 + П-4. Комитет как запись, один фронтир

**Диагноз.** Подтверждён по коду, а не по UNDERSTANDING. Шесть правил якоря из таблицы Д-1 - `[KNOWN]`: inlet `max(fin, live)` с откатом на `fin` (`dpos.rs:3762-3776`); slasher `latest_finalized_hash` + пустой ⇒ permanent (`slasher/actor.rs:826-836`); EpochTransition `read_height_for = max(n − K, anchor)` (`epoch_transition.rs:294-297`); jump `landing_hash` (`cold_start_jump.rs:667`); DkgActor `committee_read_hash` (`node/dpos.rs:1417-1420`); tombstone `block_hash(fin)` (`node/dpos.rs:1744-1746`). Четыре независимых `RethStakingStateReader` - `[KNOWN]` для `cert_inlet` (`dpos.rs:3751-3756`) и `node/dpos.rs:1411-1415`, остальные `[LIKELY]`. Д-4: пять механизмов догона - `[KNOWN]` для 1, 2, 3 (`plane_upstream.rs:198-212`), 4 (`epoch_manager.rs:1694-1726`, `:889-930`), 5 (`dpos.rs:272-330` по заголовкам).

**Осуществимость - что документ не учёл.**

1. *Снапшот комитета не константа целиком.* `getEpochCommitteeWithStakes` возвращает четыре ноги, и `tombstoned` читается **живым** при `at` (`staking-reader/src/reader.rs:662-663`, декод `:718-729`, поле `ValidatorWithKeys::tombstoned :229`); `stakes` может быть пустой, когда кольцо весов провернулось (`:668-671`). «Неизменяемая запись» П-1 верна только для `addrs`/`keys`. Tombstone watcher (`node/dpos.rs:1744-1750`, `slasher/tombstone.rs:40-49` - дельта по флагу) должен остаться живым читателем, а `weights` - полем с собственным правилом чтения. Документ включает tombstone watcher в список потребителей записи без оговорки. Это не ломает П-1, но запись получается двухслойной: frozen `(epoch, members, keys, weights@anchor)` + live overlay.

2. *Окно аутентифицируемого прыжка - 2 эпохи, не 8.* К-10: комитеты `e+1`, `e+2` закоммичены к первому блоку `e` (`[LIKELY]` реестр; комментарий `cert_inlet.rs:164-166` консервативнее - «once the finalized tip passes epoch-(E-1)-start the read is valid», то есть даёт окно в одну эпоху; по коду разница не проверялась, обе версии дают окно ≤ 2 эпох). Значит запись для `E` строится из локального finalized только при `E ≤ epoch(fin) + 2`. После П-1+П-4 прыжок к цели в эпохе `E_fin + 3` и дальше аутентифицировать нечем - независимо от `SCHEME_RETENTION_EPOCHS = 8` (`lib.rs:26`). Документ пишет «за окно `SCHEME_RETENTION_EPOCHS`»; по коду окно вдвое-вчетверо уже. На devnet-интервале 32 два эпохи = 64 блока < `JUMP_THRESHOLD` (`dpos.rs:2458`, `min(1024, interval)` = 32 на devnet) - прыжок формально возможен, но при отставании > 64 блоков узел его уже не подтвердит; остаётся последовательный догон marshal-backfill + derive каждого блока. Это не регресс безопасности, но регресс живучести, который надо назвать честно: **без checkpoint'а быстрого догона нет нигде, кроме окна двух эпох.**

3. *reth во время backfill'а игнорирует любой FCU* - `RETH:crates/engine/tree/src/tree/mod.rs:1173-1178` (`!backfill_sync_state.is_idle()` ⇒ `syncing()`, «skipping forkchoice update») `[KNOWN]`. Это закрывает половину открытого вопроса 1 документа (Э-2): честный FCU не может перенацелить запущенный к чужому хэшу backfill. Прекращается ли backfill сам, если никто не отдаёт цель - `[LIKELY]` нет (RETH_INTERNALS.md:221: загрузка повторяется без таймаута; сам код `full_block.rs` не открывал). Следовательно условие документа «если reth не возвращается честным FCU, П-4 поднимается до "сделать первым"» - выполнено по коду.

**Цена - что упущено.**
- Список «ломается» не включает: tombstone watcher как живой читатель; `WeightedVrf::try_new(&cfg.snapshot)` (`engine.rs:258`) и второй декод снапшота в `EpochEngine::new` (`:161-168`) - оба потребители формы снапшота; `check_peer_set_size`/`track_and_trigger` (`epoch_transition.rs:614-632`) читает `committee[e+1]` при том же `at` - после П-1 это вторая запись, и её отсутствие сейчас лишь `debug!`.
- Инварианты §4 UNDERSTANDING: 1, 2 названы; не назван инвариант 16 (заморозка геометрии) - таблица записей нуждается в геометрии для якоря `start(E−2)`, значит П-1 зависит от П-10 (в «Порядке» П-10 стоит первым, но зависимость не сформулирована). Непроверяемый инвариант «`highest_observed_epoch` ≤ реальная» - назван.
- Миграция: «нет» - верно для диска и wire. Но операционная: узел, отставший > 2 эпох в момент выкладки, без checkpoint'а догоняет только последовательно.

**Наполовину.** Документ: «две таблицы = класс R-075». По коду верно и опаснее: `EpochSchemeProvider::register` отвергает повторную регистрацию с другим комитетом (`outer.rs:339-346`) - две таблицы с разными якорями на одной эпохе дадут молчаливый `error!` и старую схему в marshal. Для П-4 половина «проба остаётся триггером» = R-004 остаётся - верно, и хуже: пока `upstream_frontier` жив, `maybe_re_jump` не гейтится на `awaiting_seed` намеренно (`executor.rs:1391-1397`).

**Осуществимость.**
- *Прецедент уже в коде.* `recover_replay_seed` (`dpos.rs:629-706`) и `seed_from_cert` (`:600-608`) делают ровно то, что предлагает П-2: читают финализацию по высоте из архива, сверяют `proposal.round == round`, берут `certificate.seed()`, при промахе идут в upstream. Вердикт: осознанное решение; цена (35–51 pairing на раунд) не измерена ни документом, ни реестром (нет Э-записи), «пока n ≤ 51» - без числа.
